**范围与关键决策**

本文档描述 DITING 重写后的协作翻译平台。现有网站（fork 译文集 + 稀疏覆盖 + merge request）只作为参考，不约束新设计。

1. 协作模型: 每个 (TextEntry, 目标语言) 只有一份正式译文，配合修订历史（TranslationRevision）、修改建议（TranslationSuggestion）和审核流程。不保留 fork 译文集机制；如后期确有个人变体需求，再以派生项目形式评估。  
2. 游客基线: 游客可以查看项目介绍、进度概览、发布版本和公开的问题报告（UC-21）；不能查看译文正文和编辑器。提交任何内容（评论、建议、问题报告）都需要注册登录（UC-18）。  
3. 任务范围: 任务引用条目集（EntrySet）。条目集可以按文件 / section 自动生成，也可以由管理员跨文件手动挑选条目创建（UC-03）。  
4. 贡献链: 不建立独立机制。TranslationRevision 链（作者、时间、前一版本、来源建议）就是贡献链，贡献统计和 credits 从中推导（UC-05、UC-13）。  
5. Release 语言: 版本号是项目级的，发布附件按语言标注；MVP 只做单语言发布，schema 预留多语言（UC-12）。
6. 重复句（dup）: MVP 即落地。每条原文都属于一个去重组（dup_groups），译文挂在组上而不是单条原文上；同组原文天然共享同一份译文，翻一条即全组生效,不需要镜像同步逻辑。独立句子是成员数为 1 的组。决策 1 中的 "(TextEntry, 目标语言)" 相应修正为 "(去重组, 目标语言)"。

**开发分期**

MVP 目标: 一个游戏、一种目标语言、小团队分工翻译，能从创建项目一路跑到导出可用的译文文件。

MVP 范围（每个 UC 按裁剪后执行）:

1. UC-18 注册登录: 邮箱 + 密码；不做 OAuth 和第三方绑定。  
2. UC-01 创建项目: 基础信息、封面、是否公开；不做加入申请配置。  
3. UC-02 导入资源: 一种文本格式 + 术语表导入 + 导入检查；控制码和长度规则先写在项目配置中，不做字库/字符集和规则配置界面。  
4. UC-03 任务: 只做分配制，Maintainer/Reviewer 创建条目集（含跨文件自定义挑选）并指派给译者；不做自选认领、混合制、截止时间。  
5. UC-04 成员管理: 邀请制，Maintainer 手动添加/移除成员，角色只有 Maintainer / Reviewer / Translator 三档；不做申请审核流程。  
6. UC-05 提交译文: 只做 visible\_assignment\_based，成员可查看全部文本，任务负责人可编辑，保存即产生 revision；不做修改建议和任务级 ReviewRequest。  
7. UC-06 审核: 单条审核 approve / request\_changes / reject / edit\_and\_approve；任务完成度由“集内条目全部 approved”派生，不做任务级审核状态。  
8. UC-07 质量检查: 控制码完整、长度超限、空译文，术语违反记 warning；不做字库字符和显示宽度检查。  
9. UC-10 导出: approved\_only 和 approved\_with\_fallback 两种策略、一种输出格式；不做快照导出和导出事务。  
10. UC-15 仪表盘: 进度数字、任务列表、最近活动；不做质量统计和管理面板。  
11. UC-20 术语表: Maintainer/Reviewer 直接增删改 + 冲突检测 + 编辑器术语提示；不做译者提议审批流和 needs\_recheck 联动。

MVP 状态机: untranslated / draft / waiting\_review / approved，加 needs\_changes 与 rejected 两个打回回路；translated（标记完成）状态与任务级提交一起推迟到 Phase 2。

Phase 2（有稳定协作者后）: UC-03 自选制与混合制、UC-05 修改建议、UC-08 截图等上下文素材、UC-09 评论、UC-14 通知、UC-16 重新导入与增量更新、UC-19 搜索。

Phase 3（有玩家后）: UC-11 导出事务、UC-12 发布版本、UC-13 / UC-13B 贡献统计、UC-17 审计日志、UC-21 问题报告。

**UC-02 导入项目资源**

Actor: Maintainer / Tool Maintainer

目标:  
把汉化项目需要的基础资源导入平台，包括原文文本、字库、术语表、控制码规则和上下文素材，为后续翻译、校对、质量检查和导出构建提供基础数据。

前置条件:

1. 项目已经创建。  
2. 用户拥有项目管理权限。  
3. 项目已经确定源语言。  
4. 项目已经配置至少一个目标语言。  
5. 如果是 ROM/游戏项目，已经有基本的文本提取格式或导入工具。

主要流程:

1. Maintainer 进入项目管理页面。  
2. 选择“导入项目资源”。  
3. 上传原文文本文件，例如 JSON、CSV、YAML、TXT dump 或自定义导出格式，资源语言通常等于项目源语言。  
4. 系统解析文本条目，生成 TextEntry 数据。  
5. 每条 TextEntry 保留原文、文件来源、section、entry id、顺序、上下文、控制码和技术备注。  
6. Maintainer 上传字库或字体相关文件，例如 TTF、TTC、bitmap font、字模表、码表或可用字符集文件。 如果上传的是术语表、译文字库、译文限制规则或已翻译文本，则需要指定目标语言 。  
7. 系统解析或记录项目可用字符范围，用于后续检查译文是否包含无法显示的字符。  
8. Maintainer 上传名词表 / 术语表，例如角色名、地名、技能名、道具名、店名、系统词和固定译名。  
9. 系统按照语言维度保存资源，并在对应语言的翻译界面、质量检查和导出流程中使用。   
10. 系统导入术语条目，并在翻译界面中提供提示。  
11. Maintainer 可配置控制码规则，例如哪些标签必须保留、哪些标签可以移动、哪些标签表示换行、等待、颜色、角色名或变量。  
12. Maintainer 可配置文本限制，例如最大字节数、最大显示宽度、最大行数、允许换行数量和禁用字符。  
13. 系统运行一次导入检查，报告解析失败、重复 id、缺失字段、非法控制码、未知字符或术语冲突。  
14. Maintainer 确认导入结果。  
15. 系统把项目状态更新为 ready\_for\_translation。

结果:  
项目拥有可翻译的文本条目、可用字符集、术语表、控制码规则和质量检查基础。译者可以开始认领任务并提交译文。

异常流程:

1. 如果原文文件格式无法解析，系统提示错误位置，并允许 Maintainer 下载错误报告。  
2. 如果 TextEntry id 重复，系统要求选择覆盖、跳过、合并或取消导入。  
3. 如果字库文件无法解析，系统允许先保存文件，但将字符检查状态标记为 unavailable。  
4. 如果名词表存在重复原文或冲突译名，系统生成冲突列表，交给 Maintainer 手动确认。  
5. 如果控制码规则缺失，系统仍允许导入文本，但在翻译界面中显示“控制码检查未启用”的警告。  
6. 如果部分资源缺失，项目可以进入 partial\_ready 状态，但不能执行完整质量检查或正式导出。

质量检查:

1. 原文条目是否有唯一 id。  
2. 原文条目是否保留控制码。  
3. 文件、section、entry 顺序是否完整。  
4. 字库是否覆盖目标语言所需字符。  
5. 术语表是否存在冲突译名。  
6. 控制码规则是否能识别当前文本中的标签。  
7. 导入后的文本数量是否与源文件预期一致。

**UC-03 认领或分配翻译任务**

Actor: 译者 / Reviewer / Maintainer

目标:  
让翻译任务可以通过自选认领或管理员分配两种方式进入执行状态。

主要流程:

1. 译者浏览可翻译任务列表。  
2. 如果项目允许自选，译者可以认领文件、section 或文本批次。  
3. 如果项目采用分配制，Maintainer 或 Reviewer 可以把任务分配给指定译者。  
4. 系统记录任务负责人、任务状态、开始时间和截止时间。  
5. 项目页面显示当前谁正在翻译哪个任务。

任务范围:

1. 任务引用一个条目集（EntrySet）。  
2. 条目集可以按文件、section 或 batch 自动生成。  
3. Maintainer 或 Reviewer 也可以跨文件、跨 section 手动挑选任意 TextEntry，创建自定义条目集，用于上下文分散的文本，例如同一场景的对话散落在不同文件中。  
4. 条目集创建后是显式的条目列表，不随文件结构重组（UC-16）自动变化。  
5. 同一条 TextEntry 可以属于多个条目集；系统在任务创建时提示条目重叠带来的编辑冲突风险。

任务模式:

1. 自选制: 译者主动认领任务。  
2. 分配制: 管理员指定译者负责某个任务。  
3. 混合制: 普通任务可自选，关键文本由管理员分配。

结果:  
任务进入 in\_progress 状态，并与译者绑定。

**UC-04 项目成员与权限管理**

Actor: Maintainer / Applicant / Member

目标:  
让项目可以设置加入方式、管理成员权限，并支持审核申请、移除成员和查看成员状态。

项目类型:

1. 开放项目: 用户可以直接加入或直接贡献。  
2. 申请制项目: 用户需要提交申请，Maintainer 审核后才能加入。  
3. 私有项目: 只有被邀请的用户可以查看和参与。

主要流程:

1. Maintainer 设置项目加入方式。  
2. 用户申请加入项目。  
3. 用户可填写申请理由、擅长方向、联系方式，例如 QQ 群号或 Discord。  
4. Maintainer 查看申请列表。  
5. Maintainer 批准或拒绝申请。  
6. 被批准用户成为项目成员。  
7. Maintainer 可以修改成员角色，或将成员移出项目。

权限:

1. 查看项目成员。  
2. 审核加入申请。  
3. 邀请成员。  
4. 踢出成员。  
5. 修改成员角色。  
6. 设置项目可见性和加入方式。

结果:  
项目拥有清晰的成员体系和权限控制。

**UC-05 提交译文与修改建议**

Actor:  
译者 / 项目成员 / Reviewer / Maintainer

目标:  
让用户可以根据项目协作模式，逐条编辑译文、保存版本、提交修改建议，并在需要时发起单条或任务级审核请求。

前置条件:

1. 项目已经创建。  
2. 项目已经导入原文文本。  
3. 项目已经配置目标语言。  
4. 用户拥有翻译、建议或编辑权限。  
5. 文本条目处于可编辑或可建议状态。

协作模式:

1. assignment\_based:  
   文本被拆分为多个任务。译者通常只能查看和编辑自己认领或被分配的任务。  
2. visible\_assignment\_based:  
   所有项目成员都可以查看全部文本、译文、历史版本和评论，但只有任务负责人可以直接编辑任务内文本。其他成员可以评论或提交修改建议。  
3. open\_pool:  
   所有可翻译文本进入公共文本池。项目成员可以查看全部文本，并根据权限直接编辑、保存译文或提交修改建议。  
4. hybrid:  
   普通文本开放协作，关键剧情、术语密集文本或高风险文本采用任务制。

主要流程:

1. 用户进入项目翻译页面。  
2. 系统根据协作模式显示可编辑范围。  
3. 用户打开某条 TextEntry。  
4. 系统显示原文、目标语言、上下文、已有译文、历史版本、术语提示、控制码规则和长度限制。  
5. 用户输入译文或修改建议。  
6. 系统运行自动质量检查。  
7. 如果检查出现 error，系统阻止正式提交。  
8. 如果检查只有 warning，系统允许保存，但标记风险。  
9. 如果用户有直接编辑权限，系统保存为新的 TranslationRevision。  
10. 如果用户没有直接编辑权限，或文本已锁定，系统保存为 TranslationSuggestion。  
11. 每次保存都记录作者、时间、内容、修改说明和前一个版本。  
12. 用户可以选择提交单条 TextEntry 审核。  
13. 如果用户正在处理任务，可以在完成多条文本后提交任务级 ReviewRequest。  
14. 系统记录 ReviewRequest，但不在 UC-05 中处理审核结果。

结果:  
译文被保存为可追踪版本；建议被保存为待处理建议；单条或任务级审核请求被创建。

异常流程:

1. 用户没有权限时，系统拒绝编辑。  
2. 文本被锁定时，普通用户只能提交建议。  
3. 控制码错误时，系统禁止提交审核。  
4. 多人同时修改同一条文本时，系统保留多个 revision，并标记冲突。  
5. 任务长期未提交时，Maintainer 可以在任务管理中重新分配。

状态变化:  
TextEntry:  
untranslated → draft  
draft → translated  
translated → waiting\_review  
locked → suggestion\_only

TranslationSuggestion:  
pending

ReviewRequest:  
created / waiting\_review

**UC-06 审核译文与采纳建议**

Actor:  
Reviewer / Maintainer

目标:  
让 Reviewer 审核单条译文、修改建议或任务级 ReviewRequest，并决定批准、打回、拒绝或编辑后批准。

前置条件:

1. 项目中存在 waiting\_review 状态的 TextEntry、TranslationSuggestion 或 ReviewRequest。  
2. 用户拥有 Reviewer 或 Maintainer 权限。  
3. 待审核内容已经通过基础质量检查，或带有 warning 供 Reviewer 判断。

审核对象:

1. 单条 TextEntry 译文。  
2. 单条 TranslationSuggestion。  
3. 任务级 ReviewRequest。

主要流程:

1. Reviewer 进入审核页面。  
2. 系统显示待审核列表。  
3. Reviewer 打开单条译文、修改建议或任务级 ReviewRequest。  
4. 系统显示原文、译文、提交者、历史版本、评论、术语提示、质量检查结果和上下文。  
5. 如果是单条译文，Reviewer 选择 approve、request\_changes、reject 或 edit\_and\_approve。  
6. 如果是 TranslationSuggestion，Reviewer 选择 accept、reject 或 edit\_and\_accept。  
7. 如果是任务级 ReviewRequest，Reviewer 逐条给出审核结果。  
8. 通过的条目立即合并为当前正式译文，并进入 approved / locked 状态。  
9. 不通过的条目退回修改，进入 needs\_changes 或 rejected 状态。  
10. 如果任务中同时存在通过和未通过条目，ReviewRequest 状态变为 partially\_approved。  
11. 译者修改未通过条目后，可以重新提交审核。  
12. 系统默认只重新审核被修改或未通过的条目，已 approved 条目不重复审核，除非 Reviewer 手动解锁。

结果:  
通过的译文立即生效；未通过的译文返回修改；任务级审核可以部分通过，不会因为少数问题条目阻塞全部内容。

任务级审核结果:

1. approve\_all:  
   所有条目通过，ReviewRequest 变为 approved / completed。  
2. request\_changes\_all:  
   所有条目需要修改，ReviewRequest 变为 needs\_changes。  
3. reject\_all:  
   整个提交不可用，ReviewRequest 变为 rejected。  
4. partial\_approval:  
   部分条目已合并，部分条目退回修改，ReviewRequest 变为 partially\_approved。

状态变化:  
TextEntry:  
waiting\_review → approved  
waiting\_review → needs\_changes  
waiting\_review → rejected  
approved → locked

TranslationSuggestion:  
pending → accepted  
pending → rejected

ReviewRequest:  
waiting\_review → approved  
waiting\_review → needs\_changes  
waiting\_review → rejected  
waiting\_review → partially\_approved  
partially\_approved → waiting\_review  
partially\_approved → approved

异常流程:

1. 如果译文有质量检查 error，Reviewer 不能 approve，除非 Maintainer 强制处理。  
2. 如果存在 warning，Reviewer 可以批准，但需要记录确认。  
3. 如果多个建议互相冲突，Reviewer 可以选择一个采纳，或手动合并。  
4. 如果任务问题太多，Reviewer 可以整体打回。  
5. 如果已批准条目后来发现问题，Reviewer 或 Maintainer 可以解锁并重新审核。

**UC-07 自动质量检查**

Actor:  
系统 / 译者 / Reviewer / Maintainer

目标:  
在译文保存、提交审核、审核批准和导出前，自动检查译文是否符合项目的语言和技术限制，避免破坏游戏文本或导出流程。

触发时机:

1. 译者保存单条译文时。  
2. 译者提交任务审核时。  
3. Reviewer 批准译文时。  
4. Maintainer 导出译文时。

检查内容:

1. 控制码是否完整保留。  
2. 占位符是否完整保留。  
3. 标签是否闭合。  
4. 换行数量是否符合规则。  
5. 译文是否超过最大字符数、字节数或显示宽度。  
6. 是否包含字库不支持的字符。  
7. 是否违反术语表。  
8. 是否存在空译文。  
9. 是否存在明显重复译文。  
10. 是否包含禁用字符或非法符号。

主要流程:

1. 用户保存或提交译文。  
2. 系统读取该项目的 ControlCodeRule、FontAsset、CharacterSet、Glossary 和 LengthRule。  
3. 系统对译文运行检查。  
4. 如果存在 error，系统阻止正式提交。  
5. 如果存在 warning，系统允许保存，但标记风险。  
6. 系统生成 QualityCheckResult。  
7. Reviewer 审核时可以看到检查结果。  
8. 导出前，系统再次检查所有待导出译文。

结果:  
译文拥有明确的质量检查状态，明显会破坏游戏的译文不能进入正式版本。

检查级别:

1. error:  
   必须修复，否则不能提交或导出。  
2. warning:  
   可以继续，但需要 Reviewer 注意。  
3. info:  
   仅作为提示，不阻止流程。

相关状态:  
unchecked  
passed  
passed\_with\_warnings  
failed

**UC-08 查看上下文与术语提示**

Actor:  
译者 / Reviewer / Maintainer

目标:  
让用户在翻译或审核文本时，能够看到足够的上下文信息、术语提示和历史译法，减少误译和风格不统一。

前置条件:

1. 项目已经导入原文文本。  
2. 项目可以选择性导入术语表、截图、角色信息或文本上下文。  
3. 用户拥有查看该文本条目的权限。

主要流程:

1. 用户打开某条 TextEntry。  
2. 系统显示原文、当前译文和目标语言。  
3. 系统显示该条文本所属项目、文件、section、场景或文本批次。  
4. 系统显示前后相邻文本。  
5. 如果有截图或视频时间点，系统显示对应上下文素材。  
6. 如果原文命中术语表，系统显示推荐译名、解释和术语分类。  
7. 如果该词之前出现过，系统显示历史译法。  
8. 如果存在角色、地点、道具、技能等 metadata，系统显示相关说明。  
9. Reviewer 审核时也可以查看同样上下文。

结果:  
译者和 Reviewer 可以基于上下文做出更准确、一致的翻译判断。

可显示信息:

1. 前后文本。  
2. 所属文件 / section / batch。  
3. 角色名、说话人、场景名。  
4. 截图、视频时间点或游戏位置。  
5. 术语表命中。  
6. 历史译法。  
7. 相关评论。  
8. 技术备注，例如长度限制、控制码含义。

异常流程:

1. 如果没有上下文素材，系统只显示文本位置和前后条目。  
2. 如果术语表存在冲突译名，系统显示 warning。  
3. 如果截图或素材缺失，系统显示占位提示。  
4. 如果用户没有权限查看上下文素材，系统隐藏相关内容。

**UC-09 评论与讨论**

Actor:  
译者 / Reviewer / Maintainer / 项目成员

目标:  
让项目成员可以围绕单条文本、任务、术语或项目问题进行讨论，记录翻译理由和审核意见。

前置条件:

1. 用户拥有项目查看权限。  
2. 项目中存在可讨论的 TextEntry、TranslationTask、GlossaryTerm 或 ReviewRequest。  
3. 项目允许成员评论。

讨论对象:

1. 单条 TextEntry  
2. 单条 TranslationRevision  
3. TranslationSuggestion  
4. TranslationTask  
5. ReviewRequest  
6. GlossaryTerm  
7. 项目级问题

主要流程:

1. 用户打开文本、任务、审核请求或术语页面。  
2. 系统显示已有评论。  
3. 用户发布评论。  
4. 评论可以包含翻译理由、上下文说明、术语建议或修改意见。  
5. 用户可以提及其他成员。  
6. 被提及用户收到通知。  
7. Reviewer 可以把评论标记为 resolved。  
8. Maintainer 可以删除不合适评论或关闭讨论。

结果:  
翻译过程中的争议、解释和审核意见被保留下来，方便后续回看。

评论类型:

1. general\_comment: 普通讨论  
2. review\_comment: 审核意见  
3. terminology\_comment: 术语讨论  
4. context\_note: 上下文补充  
5. issue\_report: 问题报告

权限规则:

1. Translator 可以评论自己可见的文本和任务。  
2. Reviewer 可以评论、解决讨论和添加审核意见。  
3. Maintainer 可以管理所有评论。  
4. 非成员是否能评论，由项目设置决定。

异常流程:

1. 如果评论对象已锁定，仍可评论，但不能直接修改译文。  
2. 如果用户没有查看权限，不能看到评论内容。  
3. 如果评论涉及已解决问题，系统可以提示“该讨论已 resolved”。  
4. 如果评论被删除，系统保留删除记录。

**UC-10 导出译文与生成版本**

Actor:  
Maintainer / Tool Maintainer

目标:  
把项目中已批准的译文导出为指定格式，用于本地构建、ROM 注入、补丁生成、网站展示或同步到代码仓库。

前置条件:

1. 项目已经导入原文文本。  
2. 项目中存在 approved 状态的译文。  
3. 用户拥有导出权限。  
4. 项目已经配置导出格式或导出工具。

主要流程:

1. Maintainer 进入导出页面。  
2. 选择目标语言。  
3. 选择导出范围，例如全部文本、指定文件、指定 section、指定任务或指定版本。  
4. 选择导出格式，例如 JSON、CSV、YAML、自定义文本格式、patch input 或构建工具输入文件。  
5. 系统运行导出前质量检查。  
6. 如果存在 error，系统阻止正式导出。  
7. 如果只有 warning，系统允许 Maintainer 确认后继续。  
8. 系统只导出 approved 译文；没有 approved 译文的条目可以选择保留原文、留空或跳过。  
9. 系统生成导出文件。  
10. 系统记录 ExportJob 和导出版本。  
11. Maintainer 下载导出文件，或同步到外部仓库。

结果:  
项目生成一个可追踪、可复现的译文导出版本。

导出策略:

1. approved\_only:  
   只导出已审核译文。  
2. approved\_with\_fallback:  
   已审核译文优先，未审核条目回退到原文。  
3. selected\_snapshot:  
   导出某个历史版本或指定时间点的译文快照。  
4. task\_based:  
   只导出某个任务或任务集合中的译文。

异常流程:

1. 如果导出前质量检查失败，系统生成错误报告。  
2. 如果部分条目没有 approved 译文，系统显示缺失列表。  
3. 如果导出工具失败，系统保存失败日志。  
4. 如果字库不支持部分字符，系统显示字符缺失报告。  
5. 如果导出格式和项目文本结构不匹配，系统阻止导出。

**UC-11 导出事务日志与可恢复导出**

Actor:  
Maintainer / Tool Maintainer / 系统

目标:  
作为 UC-10 导出流程的安全机制，记录导出过程中的关键步骤、错误和生成文件，确保导出失败时不会破坏上一个成功版本，并支持失败后排查、回滚或重试。

前置条件:

1. 用户在 UC-10 中发起导出。  
2. 项目存在可导出的 approved 译文。  
3. 用户拥有导出权限。  
4. 项目已经配置导出格式或构建工具。

主要流程:

1. Maintainer 在 UC-10 中发起导出。  
2. 系统创建 ExportTransaction。  
3. 系统写入 TxB，表示导出事务开始。  
4. 系统记录导出参数，例如目标语言、导出范围、导出格式、发起者和时间。  
5. 系统生成临时导出文件，而不是直接覆盖正式文件。  
6. 系统运行质量检查、格式检查和构建检查。  
7. 系统把每一步写入 ExportLog。  
8. 如果检查或构建失败，系统标记事务为 failed，并保留日志和错误报告。  
9. 如果全部成功，系统将临时文件原子提交为正式 ExportFile。  
10. 系统写入 TxE，表示事务成功结束。  
11. 系统把 ExportTransaction 标记为 committed。  
12. 用户可以在导出页面查看导出日志、错误报告和生成文件。

结果:  
导出过程可追踪。失败导出不会覆盖上一次成功文件；成功导出拥有完整日志和可复现记录。

事务规则:

1. 有 TxB 且有 TxE:  
   导出成功完成。  
2. 有 TxB 但没有 TxE:  
   导出未完成，系统视为 incomplete 或 failed。  
3. 写正式文件前必须先写临时文件:  
   防止半写入文件损坏正式导出。  
4. 正式文件替换必须是原子操作:  
   要么完全成功，要么保留旧版本。  
5. 外部构建或补丁生成失败:  
   不影响上一个成功 ExportFile。

事务状态:  
pending  
running  
committed  
failed  
rolled\_back  
incomplete

日志事件:  
TxB  
CheckStarted  
CheckPassed  
CheckFailed  
TempFileWritten  
ArtifactGenerated  
AtomicReplace  
BuildStarted  
BuildFailed  
BuildSucceeded  
TxE

异常流程:

1. 如果服务器中途崩溃，恢复后扫描没有 TxE 的 ExportTransaction。  
2. 对 incomplete 事务，系统可以丢弃临时文件或允许 Maintainer 重试。  
3. 如果日志写入失败，系统阻止正式导出。  
4. 如果导出成功但外部发布失败，ExportTransaction 仍为 committed，外部同步状态单独标记 failed。  
5. 如果正式文件损坏，Maintainer 可以回滚到上一个 committed ExportFile。

**UC-12 发布版本管理**

Actor:  
Maintainer / Tool Maintainer

目标:  
将一次成功导出或构建结果发布为项目版本，让用户可以查看、下载和追踪不同版本的汉化成果。

前置条件:

1. 项目已经创建。  
2. 项目中存在至少一次成功的 ExportTransaction。  
3. 用户拥有发布权限。  
4. 导出文件或构建产物已经通过导出前质量检查。  
5. 如果项目需要补丁文件，补丁已经成功生成。

主要流程:

1. Maintainer 进入项目发布管理页面。  
2. 选择一次成功的 ExportTransaction 或 BuildArtifact。  
3. 系统显示该次导出的目标语言、导出范围、质量检查结果、导出日志和生成文件。  
4. Maintainer 填写版本号，例如 v0.1、v1.0-beta、v1.0。  
5. Maintainer 填写发布标题和更新说明。  
6. Maintainer 选择发布类型：draft、prerelease 或 stable。  
7. Maintainer 选择要附加的发布文件，例如译文文件、补丁文件、字体文件、校验文件或说明文档。  
8. 系统创建 Release 记录。  
9. 如果选择 draft，版本只对 Maintainer 或项目成员可见。  
10. 如果选择 prerelease，版本公开但标记为测试版。  
11. 如果选择 stable，版本作为当前正式版本展示。  
12. 系统记录发布者、发布时间、关联导出事务和关联文件。  
13. 项目页面更新最新版本信息。

结果:  
一次成功导出或构建结果被保存为可追踪的发布版本，用户可以查看版本说明并下载对应文件。

发布状态:

1. draft:  
   草稿版本，只用于内部检查。  
2. prerelease:  
   测试版本，可以公开下载，但不作为最终稳定版。  
3. stable:  
   正式版本，显示为项目当前推荐版本。  
4. archived:  
   归档版本，保留历史记录，但不再推荐下载。

异常流程:

1. 如果选择的 ExportTransaction 没有成功完成，系统拒绝发布。  
2. 如果导出日志中存在未解决 error，系统拒绝发布。  
3. 如果发布文件缺失，系统提示重新选择或重新导出。  
4. 如果版本号重复，系统要求修改版本号。  
5. 如果发布后发现严重问题，Maintainer 可以撤回、归档或重新发布新版本。  
6. 如果外部同步失败，例如 GitHub Release 创建失败，平台内 Release 仍可保存，但外部同步状态标记为 failed。

权限规则:

1. Maintainer 可以创建、编辑、发布、撤回和归档版本。  
2. Tool Maintainer 可以关联构建产物和补丁文件。  
3. Reviewer 可以查看 draft / prerelease，但不能发布 stable。  
4. 普通成员是否能查看 draft，由项目设置决定。  
5. 游客只能查看公开的 prerelease、stable 和 archived 版本。

版本内容:

1. 版本号。  
2. 发布标题。  
3. 更新说明。  
4. 目标语言。  
5. 发布状态。  
6. 关联 ExportTransaction。  
7. 关联 BuildArtifact。  
8. 下载文件，每个文件标注目标语言。  
9. 文件校验值。  
10. 发布时间。  
11. 发布者。  
12. 已知问题。

**UC-13 贡献统计与署名**

Actor:  
系统 / Maintainer / 项目成员 / 游客

目标:  
统计单个项目内成员的贡献，并为项目页面和发布版本生成贡献榜、署名表和 credits。

前置条件:

1. 项目已经创建。  
2. 项目中存在用户贡献行为。  
3. 系统记录了译文提交、审核决定、建议采纳、评论、术语修改、导入导出等贡献事件。

主要流程:

1. 用户进入项目贡献页面。  
2. 系统读取该项目内的 ContributionEvent。  
3. 系统按成员、目标语言、版本、时间范围和贡献类型统计贡献。  
4. 系统显示项目贡献榜。  
5. Maintainer 可以添加手动署名，例如破解、工具、字体、测试、特别感谢。  
6. 手动署名只影响展示，不修改原始贡献记录。  
7. 发布版本时，系统根据该版本包含的贡献生成 Release credits。  
8. 用户可以在项目页面或 Release 页面查看贡献者名单。

统计内容:

1. 提交译文条目数。  
2. 被批准译文条目数。  
3. 审核条目数。  
4. 被采纳建议数。  
5. 评论数。  
6. 术语贡献数。  
7. 导入、导出、构建相关贡献。  
8. 手动署名贡献。

署名类型:  
Translation  
Review  
Proofreading  
Hacking  
Tools  
Font  
Testing  
Design  
Special Thanks

结果:  
项目贡献被长期记录，并可展示为项目贡献榜和发布版本 credits。

异常流程:

1. 如果贡献者删除账号，贡献记录保留，但公开显示名可匿名化。  
2. 如果某个译文被回滚，历史贡献保留，但可选择不计入当前版本 credits。  
3. 如果用户选择不公开署名，项目页面显示匿名贡献者。  
4. 如果贡献统计有争议，Maintainer 可以添加说明，但不能删除原始审计记录。  
5. 如果同一用户更改显示名，统计仍按 user\_id 合并。

权限规则:

1. Maintainer 可以查看完整贡献记录并编辑手动署名。  
2. 项目成员可以查看项目内公开贡献统计。  
3. 游客只能查看公开贡献榜和 Release credits。  
4. 原始 ContributionEvent 不可被普通用户修改。

**UC-14 通知系统**

Actor:  
系统 / 用户 / Maintainer / Reviewer

目标:  
在任务分配、审核结果、评论提及、建议采纳、版本发布等关键事件发生时通知相关用户，避免协作信息遗漏。

前置条件:

1. 用户已经注册账号。  
2. 用户拥有相关项目的查看权限。  
3. 系统中发生了需要通知用户的事件。

触发事件:

1. 用户被邀请加入项目。  
2. 用户的加入申请被批准或拒绝。  
3. 用户被分配翻译任务。  
4. 用户认领的任务即将到期。  
5. 用户提交的译文被批准、打回或拒绝。  
6. 用户提交的修改建议被采纳或拒绝。  
7. 用户在评论中被提及。  
8. 用户负责的任务收到新评论。  
9. Reviewer 收到新的待审核请求。  
10. Maintainer 收到新的加入申请。  
11. 项目发布新版本。  
12. 导出、构建或外部同步失败。

主要流程:

1. 系统监听项目内事件。  
2. 事件发生后，系统生成 Notification。  
3. 系统根据用户通知设置决定是否发送站内通知、邮件或外部平台通知。  
4. 用户进入通知中心。  
5. 系统显示通知列表、时间、来源项目和相关跳转链接。  
6. 用户点击通知后跳转到对应文本、任务、审核请求、评论或发布版本。  
7. 用户可以将通知标记为已读。  
8. 用户可以配置通知偏好。

结果:  
用户可以及时知道自己需要处理的任务、审核和讨论。

通知类型:

1. project\_invite  
2. join\_request\_result  
3. task\_assigned  
4. task\_due\_soon  
5. review\_result  
6. suggestion\_result  
7. mention  
8. task\_comment  
9. review\_request\_created  
10. release\_published  
11. export\_failed  
12. build\_failed

通知渠道:

1. 站内通知  
2. 邮件  
3. QQ / Discord / Telegram webhook，可后续支持

异常流程:

1. 如果用户关闭某类通知，系统只保留必要站内记录。  
2. 如果邮件发送失败，系统记录失败状态。  
3. 如果通知对象没有权限查看目标内容，系统隐藏跳转链接。  
4. 如果目标内容被删除，通知显示为 unavailable。  
5. 如果短时间内通知过多，系统可以合并为摘要通知。

**UC-15 项目仪表盘**

Actor:  
游客 / 项目成员 / Reviewer / Maintainer

目标:  
展示项目整体状态、翻译进度、审核进度、质量问题、活跃任务和最新版本，让用户快速了解项目当前情况。

前置条件:

1. 项目已经创建。  
2. 用户拥有查看项目仪表盘的权限。  
3. 项目中可以存在文本、任务、审核、导出或发布数据。

主要流程:

1. 用户进入项目主页或仪表盘页面。  
2. 系统根据用户权限显示项目概览。  
3. 系统显示项目基础信息，例如项目名称、简介、源语言、目标语言、项目状态和加入方式。  
4. 系统显示翻译进度，例如总文本数、已翻译数、已审核数、待审核数。  
5. 系统显示任务状态，例如未认领、翻译中、待审核、部分通过、已完成。  
6. 系统显示质量检查结果，例如 passed、warning、error 数量。  
7. 系统显示最近活动，例如新译文、新评论、新审核、新发布。  
8. 系统显示当前活跃成员和正在处理的任务。  
9. 系统显示最新 Release 和下载入口。  
10. Maintainer 可以查看更详细的管理数据，例如导出失败、构建失败、成员申请和待处理审核。

结果:  
项目拥有一个统一入口，用于展示进度、状态和下一步需要处理的事项。

显示内容:

1. 项目名称、封面和简介。  
2. 项目语言。  
3. 项目可见性和加入方式。  
4. 总文本数。  
5. 已翻译数量。  
6. 已审核数量。  
7. 待审核数量。  
8. 质量 warning / error 数量。  
9. 活跃任务。  
10. 待审核请求。  
11. 最近贡献。  
12. 最新发布版本。  
13. 下载入口。  
14. 加入项目入口。

权限规则:

1. 游客只能查看公开信息、公开进度和公开发布版本。  
2. 项目成员可以查看任务、成员活动和内部进度。  
3. Reviewer 可以查看待审核统计和质量问题。  
4. Maintainer 可以查看成员申请、导出状态、构建状态和管理入口。  
5. 私有项目的仪表盘只对项目成员可见。

异常流程:

1. 如果项目尚未导入文本，仪表盘显示初始化引导。  
2. 如果没有发布版本，隐藏下载入口或显示“暂无发布”。  
3. 如果质量检查未启用，显示“未配置质量检查”。  
4. 如果用户没有权限查看某些数据，系统隐藏对应模块。

**UC-16 管理项目文件与文本结构**

Actor:  
Maintainer / Tool Maintainer / Reviewer

目标:  
管理项目中的原文文件、section、文本批次和 TextEntry 结构，支持重新导入、增量更新、文本重组和任务重新划分。

前置条件:

1. 项目已经创建。  
2. 项目已经导入过原文文本或项目资源。  
3. 用户拥有项目结构管理权限。

主要流程:

1. Maintainer 进入项目文件管理页面。  
2. 系统显示项目文件结构，例如 ProjectFile、Section、Batch 和 TextEntry。  
3. Maintainer 可以查看每个文件的文本数量、翻译进度、审核进度和质量问题数量。  
4. Maintainer 可以创建、重命名、合并、拆分或归档 section。  
5. Maintainer 可以把 TextEntry 重新分组为不同 batch。  
6. Maintainer 可以重新导入原文文件。  
7. 系统比较新旧原文，识别新增、删除、修改和未变化的 TextEntry。  
8. 对未变化文本，系统保留已有译文和审核状态。  
9. 对修改过的原文，系统标记为 source\_changed，并提示需要重新检查译文。  
10. 对新增文本，系统创建新的 untranslated TextEntry。  
11. 对删除文本，系统默认归档，而不是直接删除。  
12. Maintainer 确认变更后，系统应用新的文本结构。  
13. 系统记录结构变更日志。

结果:  
项目文本结构可以被维护和更新，同时尽量保留已有翻译、审核记录和贡献记录。

支持操作:

1. 查看文件 / section / batch / TextEntry 层级。  
2. 重命名文件或 section 显示名。  
3. 合并 section。  
4. 拆分 section。  
5. 创建或调整文本 batch。  
6. 重新导入原文。  
7. 增量更新 TextEntry。  
8. 归档废弃文本。  
9. 标记原文变更。  
10. 重新生成任务。

增量导入规则:

1. id 相同、原文相同:  
   保留已有译文和审核状态。  
2. id 相同、原文变化:  
   保留历史译文，但当前译文标记为 needs\_recheck。  
3. 新 id:  
   创建新的 untranslated TextEntry。  
4. 旧 id 消失:  
   标记为 archived，不直接删除。  
5. id 冲突:  
   进入 conflict 状态，等待 Maintainer 手动处理。

异常流程:

1. 如果新文件格式无法解析，系统取消导入并保留原结构。  
2. 如果大量 TextEntry 被删除，系统要求二次确认。  
3. 如果重新分组影响已有任务，系统提示是否重新生成任务。  
4. 如果某些 TextEntry 正在审核中，系统提示变更可能影响 ReviewRequest。  
5. 如果原文变化导致已批准译文不可靠，系统自动解除 locked 状态或标记 needs\_recheck。

权限规则:

1. Maintainer 可以修改项目文本结构。  
2. Tool Maintainer 可以重新导入和处理解析结果。  
3. Reviewer 可以查看结构变化对审核的影响。  
4. Translator 只能查看自己有权限的文件和任务结构，不能修改结构。

相关状态:  
active  
archived  
source\_changed  
needs\_recheck  
conflict

**UC-17 平台管理与审计日志**

Actor:  
系统管理员 / Maintainer / 系统

目标:  
记录平台和项目中的重要操作，方便追踪责任、排查问题、回滚误操作，并提高项目安全性。

前置条件:

1. 用户已经登录。  
2. 用户执行了需要记录的重要操作。  
3. 系统已经启用审计日志功能。

主要流程:

1. 用户执行重要操作，例如修改权限、删除成员、导入资源、导出版本、审核译文或发布版本。  
2. 系统自动生成 AuditLog。  
3. AuditLog 记录操作者、操作类型、操作对象、操作时间、操作前状态和操作后状态。  
4. Maintainer 可以在项目管理页面查看本项目的审计日志。  
5. 系统管理员可以查看平台级审计日志。  
6. 用户可以按时间、操作者、操作类型和对象类型筛选日志。  
7. 如果发生误操作，Maintainer 可以根据日志定位问题。  
8. 对支持回滚的操作，Maintainer 可以发起回滚。  
9. 系统记录回滚操作本身，形成新的 AuditLog。

结果:  
关键操作被长期记录，项目可以追踪“谁在什么时候改了什么”。

需要记录的操作:

1. 项目设置变更。  
2. 成员加入、移除和权限变更。  
3. 加入申请批准或拒绝。  
4. 项目资源导入。  
5. 原文结构变更。  
6. 译文修改、回滚和锁定。  
7. 审核批准、打回和拒绝。  
8. 术语表修改。  
9. 评论删除或解决。  
10. 导出、构建和发布版本。  
11. Release 撤回、归档或重新发布。  
12. 质量检查规则变更。  
13. 字库、字符集和控制码规则变更。

日志内容:

1. 操作者 user\_id。  
2. 操作类型 action\_type。  
3. 操作对象 object\_type / object\_id。  
4. 所属项目 project\_id。  
5. 操作前数据 before\_snapshot。  
6. 操作后数据 after\_snapshot。  
7. 操作时间 created\_at。  
8. IP、设备或会话信息，可选。  
9. 备注 message。

异常流程:

1. 如果操作失败，系统记录 failed action 和错误原因。  
2. 如果用户没有权限，系统记录 permission\_denied。  
3. 如果日志写入失败，系统阻止高风险操作，或写入 fallback log。  
4. 如果对象被删除，日志仍保留对象快照。  
5. 如果用户删除账号，日志中 user\_id 可以保留，公开显示名匿名化。

权限规则:

1. Maintainer 可以查看本项目审计日志。  
2. 系统管理员可以查看平台级审计日志。  
3. 普通成员默认不能查看完整审计日志。  
4. 涉及安全、IP、设备信息的日志只对系统管理员可见。  
5. 审计日志不能被普通用户编辑或删除。

Actor:  
游客 / 用户 / 系统

目标:

主要流程:

1. 游客选择注册方式: 邮箱 + 密码，或第三方 OAuth，例如 GitHub、Google，可后续支持。  
2. 系统检查邮箱是否已被注册。  
3. 系统发送验证邮件，账号进入 unverified 状态。

6. 系统创建会话，记录登录时间和设备信息。

用户拥有可登录的账号，后续所有贡献行为都与 user\_id 绑定。

账号状态:  
unverified  
active  
disabled

异常流程:

1. 如果邮箱已被注册，系统提示直接登录或找回密码。

4. unverified 账号可以浏览游客可见内容，但不能提交任何内容。  
5. disabled 账号登录时，系统提示账号已被停用。

权限规则:

1. 注册和登录对所有游客开放。  
2. 停用账号只能由系统管理员操作。  
3. 账号删除遵循 UC-13 / UC-17 的匿名化保留规则。

目标:  
让用户按关键词搜索原文、译文、说话人、条目 id、术语和评论，并保证搜索结果严格遵守查看权限，不成为越权读取内容的旁路。

3. 如果结果数量过大，系统分页并提示收窄范围。

**UC-20 术语表管理**

Actor:  
Maintainer / Reviewer / 译者

目标:  
让项目可以创建和维护术语表，处理译名冲突，并在术语变更时提示受影响的已翻译文本，保证译名全项目一致。

前置条件:

1. 项目已经创建。  
2. 用户拥有对应的术语权限。

主要流程:

1. 用户进入项目术语表页面。  
2. 系统按分类显示术语: 角色名、地名、技能名、道具名、系统词等。  
3. Maintainer 或 Reviewer 可以直接创建和编辑术语: 原文、推荐译名、别名、分类、说明、示例。  
4. 译者可以提交术语建议，由 Reviewer 或 Maintainer 批准后生效。  
5. 系统检测冲突: 同一原文存在多个推荐译名时标记 conflict，交由 Reviewer 处理。  
6. 术语生效后，翻译界面和质量检查（UC-07、UC-08）自动使用新术语。  
7. 术语的推荐译名发生变更时，系统找出命中该术语且已翻译的条目，标记为 needs\_recheck 并提示批量复查。  
8. 删除术语时默认标记为 deprecated，保留历史引用，不物理删除。  
9. 术语支持批量导入和导出，衔接 UC-02。  
10. 每条术语支持讨论，衔接 UC-09 的 terminology\_comment。

结果:  
项目拥有单一可信的术语来源，术语变更的影响范围可追踪。

术语状态:  
proposed  
approved  
conflict  
deprecated

异常流程:

1. 如果导入的术语与已有术语冲突，进入 conflict 状态等待处理。  
2. 如果术语被大量条目引用，变更前系统显示影响数量并要求确认。  
3. 如果译者无直接编辑权限，其修改一律作为 proposed 建议保存。  
4. 如果两个术语的原文互为子串，质量检查按最长匹配优先。

**UC-21 问题报告（Issue）**

Actor:  
玩家（已登录用户）/ 游客 / 项目成员 / Reviewer / Maintainer

目标:  
让玩家和项目成员报告汉化补丁中的问题，例如错字、误译、文本溢出、显示错误或崩溃，并让项目方对问题进行分流、定位、修复和关闭。

前置条件:

1. 项目存在公开发布版本，或项目成员在内部测试中发现问题。  
2. 提交问题需要登录账号；游客可以查看公开问题列表。

主要流程:

1. 用户进入项目问题页面。  
2. 系统显示公开问题列表，可按状态、类型、版本和标签筛选。  
3. 已登录用户创建问题: 填写标题、描述、问题类型、发现问题的 Release 版本，可附截图或存档位置说明。  
4. 系统提示相似问题，减少重复提交。  
5. Maintainer 或 Reviewer 分流问题: 确认、标记重复、标记无效或请求补充信息。  
6. 项目成员可以把问题关联到具体 TextEntry 或条目集，转入翻译修复流程（UC-05）。  
7. 相关译文修复并通过审核后，问题标记为 resolved，并记录修复所在的 Release 版本。  
8. 问题下支持评论讨论，衔接 UC-09；状态变化通知报告者，衔接 UC-14。  
9. 新 Release 发布时，可以在更新说明中列出本次修复的问题。

结果:  
玩家反馈形成可追踪的闭环: 报告 → 分流 → 定位到文本 → 修复 → 随版本发布。

问题类型:

1. typo: 错字、标点错误。  
2. mistranslation: 误译、语气不符。  
3. overflow: 文本溢出、换行错误。  
4. display: 字库缺字、乱码、控制码显示异常。  
5. crash: 导致游戏异常或卡死。  
6. other: 其他问题。

问题状态:  
open  
confirmed  
in\_progress  
resolved  
wont\_fix  
duplicate  
invalid

异常流程:

1. 如果游客尝试提交问题，系统引导注册登录（UC-18）。  
2. 如果问题与已有问题重复，标记 duplicate 并链接到原问题。  
3. 如果报告缺少必要信息，标记 needs\_info，长期无补充可自动关闭。  
4. 如果问题涉及未公开内容，Maintainer 可以将其设为仅项目内可见。  
5. 如果问题被恶意刷屏，Maintainer 可以锁定问题或限制该用户提交。

权限规则:

1. 游客可以查看公开问题，不能提交、评论或投票。  
2. 已登录用户可以提交问题、补充信息和评论。  
3. Reviewer 可以分流问题、关联文本和标记状态。  
4. Maintainer 可以管理全部问题，包括设为项目内可见、锁定和删除。  
5. 私有项目的问题只对项目成员可见。
